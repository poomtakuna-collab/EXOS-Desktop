# Snapshot Payload Inspection Report

Status: inspection complete.

This report inventories the current Daily Research Snapshot save path and identifies gaps for a future Snapshot Payload v2 contract. It is documentation only. No schema, payload, persistence, or frozen analysis engine behavior was changed.

## Save Path

Manual Desktop save path:

1. `ResearchPanel.refresh()` loads a `CanonicalResultV1` through `load_desktop_research_view_model()`.
2. `load_desktop_research_view_model()` reads OHLCV rows, runs `analyze_symbol_v2()`, then calls `_canonical_result_from_analysis()`.
3. `_canonical_result_from_analysis()` starts with `build_canonical_result_v1(analysis_result)` and adds context, strategy, and signal summary sections.
4. `ResearchPanel._save_signal()` calls `save_manual_signal_candidate(canonical_result)`.
5. `save_manual_signal_candidate()` builds a compatibility `SignalRecord`, creates `SQLiteSignalLedgerRepository` and `SQLiteDailyResearchSnapshotRepository`, and calls `_save_with_repository()`.
6. `_save_with_repository()` saves the full canonical snapshot first with `snapshot_repository.save_snapshot(...)`, then saves the compatibility signal row.
7. `SQLiteDailyResearchSnapshotRepository.save_snapshot()` inserts one immutable row into `daily_research_snapshots`.

Backfill path:

1. `backfill_missing_research_signals()` loads OHLCV rows from a `MarketDataSource`.
2. For each missing market date it calls `_canonical_result_for_market_date()`.
3. `_canonical_result_for_market_date()` runs `analyze_symbol_v2()`, calls `build_canonical_result_v1()`, and adds a minimal `signal_summary`.
4. The same `save_manual_signal_candidate(..., snapshot_repository=...)` path persists the record.

Related but separate path:

- `src/statistics/snapshot_store.py` persists Market Learning rows into `snapshots`.
- That table stores `snapshot_json` plus searchable columns and is not the Daily Research Snapshot v2 table.

## Duplicated Fields

- `symbol`, `timeframe`, and date values are duplicated across `daily_research_snapshots` columns, `canonical_snapshot_json.identity`, and `canonical_snapshot_json.signal_summary`.
- `signal_id` appears in the daily snapshot row and in `signal_ledger_signals`.
- `source` appears in the daily snapshot row, `identity.source`, `identity.pipeline_name`, `diagnostics.source_pipeline`, and Signal Ledger `snapshot_source`.
- Prediction fields are duplicated between `brain.probability`, `brain.projection`, `brain.prediction_summary`, flattened `prediction`, and `signal_summary.prediction_summary`.
- Context and strategy summaries are duplicated between typed `context`/`strategy` sections and `signal_summary.context_summary`/`signal_summary.strategy_summary`.
- Market snapshot identity can be represented both by `snapshot_record_id` and legacy/canonical `snapshot_id`; only `snapshot_record_id` is guaranteed by the current v2 daily snapshot repository.

These duplications are useful for compatibility and querying, but Snapshot Payload v2 should define canonical ownership for each value.

## Current Gaps For A Lossless Snapshot

The current daily snapshot row is lossless only relative to the `CanonicalResultV1` object handed to the repository. It is not lossless relative to the full analysis run.

Missing or incomplete areas:

- Full analysis request is not persisted as a first-class section: requested symbol, timeframe, flags, start/end dates, row limit, run id, and run name are only partially recoverable.
- Input OHLCV rows used to calculate the snapshot are not stored in the daily snapshot payload. Only row counts and derived snapshot outputs are stored.
- Data source provenance is partial. The payload keeps `data_source_metadata`, but does not guarantee database path, query window, cutoff date, provider identity, or cache/read-only mode.
- Analysis cutoff details are not stored as a typed payload section. `chart_latest_date` and `analysis_cutoff_date` are used in the UI but are not persisted into `CanonicalResultV1`.
- Full `AnalysisPipelineV2Request` is not serialized. The stored canonical JSON contains results, not the exact request envelope.
- Full `CanonicalAnalysisResultV2` is not serialized. It is adapted into `CanonicalResultV1`, which drops some source object detail.
- Strategy is present for manual Desktop saves but not consistently present for backfill snapshots.
- Context is present for manual Desktop saves but not consistently present for backfill snapshots.
- Backtest is normally absent because Research saves use `include_backtest=False`.
- Similar pattern input library is not stored as input provenance; only resolver output and counts are retained.
- Runtime environment/version information is thin: adapter versions are present, but app version, code revision, database schema version, and deterministic engine versions are not consistently captured.
- The immutable record identity does not include payload hash. This is intentional for conflict detection, but it means same identity plus changed payload conflicts rather than coexisting.
- `created_at` is currently a market date from the signal, not a true creation timestamp, so audit timing is incomplete.

## Fields That Should Not Be Stored In Snapshot Payload v2

Snapshot Payload v2 should remain a daily research fact. It should not embed mutable or unrelated application state:

- Market data cache tables or unrelated OHLCV cache state beyond the exact analysis input/provenance needed for reproducibility.
- Outcome records, performance summaries, win rates, and evaluation results that are calculated after the snapshot date.
- User settings, UI layout, selected tab, dock state, and theme preferences.
- Database paths, local machine paths, credentials, API keys, broker/live account state, or GPT/AI request data.
- Backtest run persistence records unless the snapshot explicitly represents a backtest-enabled analysis mode.
- Future rows for ordinary daily research snapshots; those belong to outcome/backtest evaluation unless a specific validation snapshot type is designed.

## Recommended Snapshot Payload v2 Structure

The next payload contract should be explicit and versioned separately from the existing `daily_research_snapshot_v2` storage version:

Implementation plan for Snapshot Payload v2:

1. Define a new `SnapshotPayloadV2` dataclass/module separate from `CanonicalResultV1`.
2. Add a pure builder that consumes `CanonicalAnalysisResultV2`, exact input rows/provenance, context summaries, strategy result, and signal summary.
3. Keep the existing daily snapshot table unchanged initially by storing the new payload in `canonical_snapshot_json` only when explicitly enabled or after compatibility review.
4. Preserve `SignalRecord` compatibility generation as a projection, not the canonical snapshot payload.
5. Add tests that compare a saved payload to the exact analysis input envelope and verify no outcomes, settings, cache tables, or UI state are embedded.
6. Add a developer-only export command/view after the payload contract is stable, so one stored snapshot can be inspected without changing persistence.

## Recommendation

Treat the current implementation as a useful v1 canonical-result snapshot stored in a v2 daily-snapshot table. For true Snapshot Payload v2, add a dedicated payload contract that captures request, provenance, exact analysis inputs, deterministic outputs, summaries, diagnostics, and compatibility projections with clear ownership for duplicated fields.
